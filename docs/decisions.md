# Архитектурные решения (ADR)

Зафиксированные решения и их обоснование. Формат каждого: **решение → почему → альтернатива и
компромисс**. Документ отражает текущее состояние кода, а не историю миграций.

---

## Р1 — Web-API консоли вместо публичного API

**Решение:** ходить в `console.cloud.ru/aicloud/ui` (тот же бэкенд, что у web-консоли), а не в
публичный ML Space API.

- ➕ Богаче по данным, не требует `x-api-key`, авторизуется обычным OIDC Bearer.
- ➕ Совпадает с тем, что реально делает веб-консоль — поведение легко сверять в DevTools.
- ➖ Это внутренний контракт: эндпоинты могут меняться. Но команда контролирует и фронт, и бэкенд.

Публичный API требовал связки `service_auth` → Bearer + per-workspace `x-api-key` + `x-workspace-id`,
то есть заведения сервисного аккаунта и ключей — лишняя бюрократия для пользователя.

## Р2 — OIDC-токен через захват из браузера (без регистрации OAuth-клиента)

**Решение:** получать access-token так же, как веб-консоль — открыть браузер на `console.cloud.ru`,
дать пользователю войти по SSO и прочитать cookie `iframe_auth_cookie` через CDP. Профиль браузера
сохраняется, обновление токена идёт тихо в headless.

- ➕ Никакой регистрации публичного OAuth-клиента в IAM (внешняя зависимость + ревью безопасности).
- ➕ «Вход через Cloud.ru» как в вебе, без ручного ввода ключей.
- ➖ Нужен системный браузер на машине пользователя (Chrome/Chromium/Edge).

Авторизационный код + PKCE на клиенте консоли заблокирован (`invalid_redirect_uri`), поэтому захват
cookie — рабочий путь.

## Р3 — Встраивание веб-UI через SSH-туннель, а не через OIDC-прокси

**Решение:** открывать веб-UI ноутбука, пробрасывая SSH-туннель прямо к JupyterLab в поде (`:8888`,
поднят без токена) и ставя перед ним локальный прокси (shim), снимающий запреты на фрейминг.

- ➕ Обходит OIDC-прокси, который не принимает минтируемые токены и шлёт `X-Frame-Options: DENY` /
  CSP `frame-ancestors`.
- ➕ Тот же туннель переиспользуется для удалённого ядра.
- ➖ Требует SSH-доступа (ключ ML Space). Это приемлемо: ключ всё равно нужен для файлов/IDE.

Прокси-вариант (внедрять токен/cookie в OIDC-прокси) отвергнут: прокси принимал только интерактивную
cookie `authservice_session`, а в корпоративной сети Node→прокси давал 504.

## Р4 — Доверие системному хранилищу CA (корпоративный TLS-перехват)

**Решение:** запросы к API идут не через глобальный `fetch`, а через `consoleHttp.ts` поверх
`https.request` с агентом из `upstreamAgent.ts`, который добавляет системные корневые сертификаты
(`tls.getCACertificates("system")`).

- ➕ Работает за корпоративным прокси, пересоздающим TLS-сертификаты, где `fetch` падает с
  `fetch failed` (Node доверяет только встроенному списку CA).
- ➖ Свой тонкий http-клиент вместо `fetch` (распаковка gzip/deflate/br вручную). Зато без внешних
  зависимостей.

`undici`-диспетчер не подошёл: пакета в проекте нет, а сторонний `Agent` не проходит `instanceof`-
проверку встроенного `fetch`.

## Р5 — Выбор воркспейса плоским списком

**Решение:** получать воркспейсы одним запросом `GET /user/v1/workspaces/` (плоский список всех
воркспейсов пользователя) и показывать один QuickPick.

- ➕ Один вызов, минимум кликов — как «список, из которого просто выбираешь».
- ➖ Не группирует по проектам.

Альтернатива «организация → проект → воркспейс» (`/customers/me` → `/simple-projects` →
`/organisation/v2/workspaces/search`) отвергнута: больше шагов, а `workspaces/search` отдавал
`HTTP 400 invalid argument`. Плоский эндпоинт — тот же, что использует свитчер в шапке консоли.

---

## Р6 — Определение пути веб-UI пробой, а не по типу образа

**Решение:** перед встраиванием делать лёгкий GET через туннель и брать путь, отдавший валидный
ответ (`<prefix>/lab` для JupyterLab, `/` для marimo/VS Code-образов и пр.).

- ➕ Работает для всех типов образов без хрупких эвристик по имени образа/URL.
- ➖ +1 короткий запрос при открытии. Незаметно на фоне поднятия туннеля.

Эвристика «jupyter по подстроке в образе/URL» ошибалась (marimo в том же namespace реестра содержал
«jupyter»).

## Р7 — Чистые модули + инъектируемый клиент для тестируемости

**Решение:** логику без `vscode` (маппинг DTO, разбор URL, заголовки, ошибки, resume-body,
SSH-config) держать в отдельных модулях и покрывать юнит-тестами; сетевые клиенты принимают
`fetchImpl`.

- ➕ Быстрые детерминированные тесты без запуска VS Code и без сети.
- ➖ Чуть больше «швов» в коде. Окупается стабильностью тестов.

---

## Р8 — Инструменты: pnpm + esbuild

**Решение:** пакетный менеджер — **pnpm** (версия закреплена), бандлер — **esbuild**; `puppeteer-core`
и `ssh2` помечены `external` и едут из `node_modules`, остальное бандлится в `dist/extension.js`.

- ➕ Быстрая сборка, маленький бандл, корректная упаковка тяжёлых/нативных зависимостей в `.vsix`.

## Открытые вопросы

- Свести количество SSH-подключений к одному на ноутбук (сейчас файлы / ядро / встраивание могут
  поднимать до трёх).
- Монтирование S3 `/mnt` как multi-root папок.
- Предсборка vscode-server в образ для ускорения полного IDE-режима.
- Глубокие ссылки на страницы консоли (мониторинг, создание). Сейчас команды «Открыть мониторинг…» и
  «Создать в консоли…» открывают корень консоли (`cloudru.console.url`): точный SPA-маршрут микрофронта
  `env-jupyter-server` резолвится шеллом консоли в рантайме и недоступен из репозитория. Когда маршрут
  известен — собрать URL `.../{name}/monitoring?region=&ws=` и подставить его.
