# Аудит и план улучшений Cloud.ru Distributed Train Notebooks

Дата: 18 сентября 2026. База аудита: `main`, commit `58fe5d5`.

## Цель и границы

После реализации пользователь видит достоверное состояние текущего воркспейса, понимает ход и результат каждой операции, может восстановиться после ошибки, а файловые операции сохраняют данные и выполняются на выбранном сервере.

Этот документ — план, а не реализация. Исходники и тесты не изменены. Проверены код расширения, manifest, существующие тесты, сборка и документация. Живой вход в Cloud.ru, реальные SSH-соединения, Extension Development Host и визуальная проверка в VS Code/Cursor не выполнялись. Ниже эти проверки явно выделены; прохождение unit-тестов не доказывает корректность живого UI.

Метки доказательности:

- **Воспроизведено** — исполнен текущий код с контролируемыми зависимостями, наблюдался дефект.
- **Код** — путь и причина установлены чтением реализации; конкретный пользовательский сценарий ещё нужно воспроизвести регрессионным тестом перед исправлением.
- **UX** — предложение по улучшению поведения, а не доказательство падения.
- **Риск** — требует проверки внешнего контракта или редактора.

Приоритеты: **P0** — риск потери/перезаписи данных, исправить до расширения использования; **P1** — нарушенная корректность состояния, подключения или безопасности; **P2** — UX, диагностика и сопровождение.

## Находки

### A01 · P0 · SFTP-копирование пишет на неверный сервер — воспроизведено

**Где:** [sftpFs.ts](../src/ssh/sftpFs.ts), `copy`, строка 168.

`copy(A:/source, B:/target)` получает SFTP только для `source.authority`, а путь назначения использует без проверки authority. В локальном воспроизведении запись ушла в `A:/target`; соединение B вообще не запрашивалось. Если на A есть такой путь и разрешён overwrite, возможна перезапись постороннего файла. В `rename` аналогичный случай уже запрещён.

**Предложение:** первым шагом явно запретить cross-authority copy по образцу `rename`. Поддержку переноса между серверами рассматривать отдельно, если она нужна продукту. Также до создания назначения запрещать копирование каталога в себя/свой потомок: нынешняя рекурсия обходит уже созданную вложенную копию.

**Приёмка:** разные authority → ошибка до любых read/write; вложенное назначение → ошибка до mkdir; обычное копирование внутри сервера работает.

### A02 · P0 · Переименование уничтожает назначение до успеха — воспроизведено

**Где:** [sftpFs.ts](../src/ssh/sftpFs.ts), `rename`, строки 153–157.

При `overwrite: true` существующее назначение рекурсивно удаляется, затем вызывается `sftp.rename`. Если rename не удался, назначение уже потеряно. Это воспроизведено принудительной ошибкой rename. Переименование пути в самого себя тоже требует защиты перед удалением.

**Предложение:** проверить поддержку атомарного replace установленным `ssh2` и реальным шлюзом. При отсутствии безопасного механизма явно отказывать в destructive replace; не эмулировать его через предварительное удаление. Сохранять исходное назначение при любой ошибке.

**Приёмка:** ошибка rename, одинаковые пути, непустой каталог назначения, overwrite=false — ни один существующий файл не потерян.

### A03 · P1 · Поздний ответ меняет текущий воркспейс — воспроизведено

**Где:** [notebooksTree.ts](../src/views/notebooksTree.ts), `getChildren:162`, `applyNotebooks:88`; [index.ts](../src/commands/index.ts), `pollUntil:584`; [extension.ts](../src/extension.ts), обработчик смены воркспейса:103.

Кеш дерева не имеет принадлежности к воркспейсу/поколению сессии. Запрос A → выбор B → успешный ответ B → поздний ответ A приводит к отображению A при выбранном B. Это воспроизведено. Поллинг тоже безусловно передаёт список в `applyNotebooks`. При ошибке первой загрузки B `render()` может вернуть сохранённый список A. Затем команда берёт ноутбук из старой строки и workspace из текущей сессии.

**Предложение:** привязать применение результатов и элементы дерева к workspace и поколению сессии; сразу очищать данные прежнего контекста; игнорировать поздние результаты. Проверять принадлежность элемента перед мутацией. Аналогичную защиту применить к preflight и списку kernel servers.

**Приёмка:** A→B с любым порядком ответов, ошибка B, logout во время загрузки и смена workspace во время poll не возвращают данные A и не отправляют действия с неверным workspace.

### A04 · P1 · Успешный поллинг не снимает ошибку списка — воспроизведено

**Где:** [notebooksTree.ts](../src/views/notebooksTree.ts), `applyNotebooks:88`, `getChildren:170`, `syncFilterIndicators:212`.

`applyNotebooks` обновляет данные и снимает необходимость fetch, но не очищает `loadError`, контекст `cloudru.loadError` и сообщение дерева. В воспроизведении после успешного списка от poll продолжала показываться ошибка `offline`.

**Предложение:** один существующий путь применения успешного списка для fetch и poll: данные, ошибка, контексты и message обновляются вместе. При кешированных данных показывать «Не удалось обновить, показаны данные на …», а не ошибку первоначальной загрузки.

**Приёмка:** error→poll success снимает ошибку сразу, в том числе при пустом результате; фильтр и актуальный preflight остаются видимыми.

### A05 · P1 · Выход и смена контекста не охватывают SFTP — код

**Где:** [extension.ts](../src/extension.ts), строки 92–111; [sftpFs.ts](../src/ssh/sftpFs.ts), `connections`, `sftpFor:223`; [sshConfig.ts](../src/ssh/sshConfig.ts), `resolveSilently:76`.

Auth/workspace handlers закрывают webview и kernel tunnels, но не SFTP. Lifecycle-инвалидация в `commands/index.ts:40` тоже пропускает SFTP. Сохранённый target можно восстановить без проверки сессии и текущего workspace. UI сообщает о выходе, но смонтированные папки могут продолжать работать через сохранённый SSH-ключ.

**Предложение:** согласовать контракт выхода: для управляемых расширением соединений рекомендовано закрытие и блокировка восстановления до нового входа; при pause/delete инвалидировать SFTP конкретного ноутбука. Не закрывать внешний Remote-SSH процесс насильно; явно описать его независимость. Для грязных редакторов предусмотреть понятный сценарий сохранения локальной копии.

**Приёмка:** после logout/смены workspace старый mount не делает скрытого reconnect; pause→resume восстанавливает новое соединение; существующие открытые документы не теряются.

### A06 · P1 · SSH override одного workspace применяется к другому — код

**Где:** [sshConfig.ts](../src/ssh/sshConfig.ts), `ensureEndpoint:305`, `saveEndpoint:408`, `saveTarget:125`.

Override хранится по региону, но содержит `accountId`, зависящий от workspace. После настройки A и выбора B в том же регионе override A имеет приоритет над namespace B. Targets также не помечены workspace/account.

**Предложение:** ключ кеша должен учитывать workspace и аккаунт; существующие региональные записи безопасно сбросить или мигрировать только при доказанной принадлежности. Инвалидировать соединения после смены ключа/endpoint.

**Приёмка:** два workspace одного региона и два аккаунта не разделяют accountId; новая конфигурация используется всеми новыми подключениями.

### A07 · P1 · SSH не проверяет ключ сервера — код

**Где:** [connection.ts](../src/ssh/connection.ts), строка 135; аналог безопаснее — [sshConfigFile.ts](../src/ssh/sshConfigFile.ts), строка 35.

`hostVerifier: () => true` принимает любой ключ сервера. Подлинность SSH-шлюза не проверяется, хотя Remote-SSH использует `StrictHostKeyChecking accept-new`.

**Предложение:** использовать единый контракт доверия к host key: доверенный fingerprint либо явное подтверждение первого подключения и отказ при изменении. Не делать безусловный bypass при ошибке проверки. Способ получения эталонного fingerprint согласовать с владельцем шлюза.

**Приёмка:** известный ключ принят, другой ключ того же host/port отвергнут до передачи пользовательских данных, ошибка объясняет безопасный путь восстановления.

### A08 · P1 · Авторизация смешивает сбой среды и истечение сессии — код

**Где:** [tokenProvider.ts](../src/console/tokenProvider.ts), `getAccessToken:125`, `doMint:160`, `signOut:94`; [tokenProvider.test.ts](../test/unit/tokenProvider.test.ts).

Отсутствие Chrome возвращает undefined, которое трактуется как истечение SSO. Ошибка навигации проглатывается, затем тот же исход наступает по таймауту. Существующий тест даже моделирует expired session через отсутствие браузера. Logout не отменяет выполняющийся mint: поздний mint может снова записать cached token, а `getAccessToken` проверяет кеш раньше признака входа. Отмена между проверкой signal и завершением `puppeteer.launch` также требует отдельной проверки.

**Предложение:** различать отмену, отсутствие браузера, сетевую/навигационную ошибку и подтверждённую потерю SSO. Отменять mint при logout/dispose и запрещать применение результата старого поколения. Проверять cookie не только по имени, но и по ожидаемому домену. Не удалять lock общего browser profile без проверки владельца: сериализация `chain` действует только в одном extension host.

**Приёмка:** offline не разлогинивает; нет Chrome → одна ошибка с настройкой пути; logout во время mint не возвращает токен; отмена launch закрывает появившееся окно; два окна редактора не повреждают общий профиль.

### A09 · P1 · Повторный 401 обрабатывается по-разному — код

**Где:** [apiClient.ts](../src/console/apiClient.ts), `send:270`; [notebooksTree.ts](../src/views/notebooksTree.ts), catch:178; [serverProvider.ts](../src/jupyter/serverProvider.ts), catch:50; [pollLoop.ts](../src/console/pollLoop.ts), catch:63.

После неудачного обновления токена API может вернуть `ApiError(kind=auth)`. Только command wrapper вызывает `handleExpiredSession`; дерево распознаёт лишь `NotSignedInError`, provider возвращает пустой список, poll считает auth-ошибку транспортной и повторяет её до пяти раз. Комментарий provider о prompting не соответствует фактическому вызову в этой ветке.

**Предложение:** единый путь обработки окончательной auth-ошибки для всех потребителей. Для 403 и ошибок схемы не повторять транспортный polling; для 429 учитывать уже распарсенный Retry-After.

**Приёмка:** двойной 401 из дерева/kernel/poll → один reauth prompt и прекращение запросов; 403 не превращается в пять попыток и «потеряна связь».

### A10 · P1 · HTTP-запрос не гарантирует завершение — код

**Где:** [consoleHttp.ts](../src/console/consoleHttp.ts), строки 55–73.

Ответ слушает `data/end`, но не `aborted/error/close` при неполном теле. Обрыв после заголовков может оставить promise незавершённым. `req.setTimeout` задаёт socket inactivity timeout, а не общий deadline: медленная непрерывная передача продлевает операцию. Буфер тела не ограничен; это существенно для загрузки логов.

**Предложение:** завершать promise с исходной ошибкой при оборванном ответе, добавить общий deadline и передачу отмены; очищать таймеры/слушатели во всех исходах. Для больших логов отдельно определить допустимый объём и способ сохранения без нескольких полных копий в памяти.

**Приёмка:** локальный сервер обрывает тело после headers; другой отправляет маленькие части бесконечно; отмена во время чтения. Каждый сценарий завершается за заданный срок без зависших handles. Проверить повреждённый gzip и сохранение причины ошибки.

### A11 · P1 · Повторные lifecycle-команды и неоднозначный retry — код

**Где:** [index.ts](../src/commands/index.ts), `pauseNotebook:182`, `resumeNotebook:201`, `deleteNotebook:287`, `withErrorHandling:615`.

Прогресс начинается после mutation request, локальной блокировки notebook нет. До ответа сервера строка остаётся в прежнем статусе и позволяет повторный запуск. При network error «Повторить» запускает всё тело команды заново, хотя сервер мог уже принять POST. Подтверждение удаления/другие await также оставляют время для смены контекста.

**Предложение:** локальное состояние операции по workspace+uid с первого клика; повторный вызов присоединяется к нему или объясняет, что операция уже идёт. После неопределённого результата мутации сначала сверять серверное состояние; не обещать идемпотентность без контракта API. Показывать фазы «Отправка запроса» и «Ожидание статуса».

**Приёмка:** двойной клик → один POST; POST принят, ответ потерян → восстановление через GET; смена workspace во время подтверждения не отправляет действие в другом контексте.

### A12 · P1 · Неполные исходы и отмена поллинга — код / UX

**Где:** [pollLoop.ts](../src/console/pollLoop.ts), строки 48–78; [index.ts](../src/commands/index.ts), `pollUntil:584`.

Отмена проверяется до запроса и после применения результата, но не прерывает сам запрос/задержку. Deadline тоже не ограничивает длительность `list()`. Delete не задаёт `isFailed`, поэтому терминальная ошибка может ждать полного timeout. Cancel закрывает наблюдение, но серверная операция продолжается — UI этого не сообщает. Прогресс не показывает текущую стадию вроде ожидания ресурсов.

**Предложение:** передавать cancellation/deadline до транспорта; прекращать применение результата при смене контекста. Согласовать terminal predicates для каждой операции. Назвать cancel «прекратить отслеживание» в объяснении; после отмены сохранять серверный переходный статус и возможность снова наблюдать.

**Приёмка:** cancel во время GET, timeout, delete→error, resume→rejected, удаление другим клиентом, logout во время poll. Каждый исход понятен и не создаёт ложного успеха.

### A13 · P1 · Одновременные открытия и поздние подключения — код

**Где:** [notebookController.ts](../src/jupyter/notebookController.ts), `ensureShim:51`; [serverProvider.ts](../src/jupyter/serverProvider.ts), `ensureForward:81`, `disposeAll:118`; [sftpFs.ts](../src/ssh/sftpFs.ts), `sftpFor:223`.

Нет дедупликации выполняющегося создания shim/forward. Два вызова могут создать два ресурса и перезаписать map, оставив первый без владельца. `disposeAll` не запрещает позднему async-вызову зарегистрировать новый ресурс. У server provider `disposeAll` не очищает карту notebooks. При ошибке открытия не все частично созданные ресурсы закрываются.

**Предложение:** повторить локальный паттерн in-flight из `ConsoleApiClient`, добавить поколение/признак завершения и cleanup при failure. Проверить late completion после invalidate/dispose. При разрыве соединения не закрывать вкладку с несохранённой работой без понятного переходного экрана.

**Приёмка:** два открытия одного uid создают один ресурс; logout во время connect не оставляет порт/панель; failed forward закрывает соединение; повторное открытие после ошибки работает.

### A14 · P1 · Отмена Remote-SSH не завершает зависшую фазу — код / UX

**Где:** [connection.ts](../src/ssh/connection.ts), `exec:81`; [serverPreseed.ts](../src/ssh/serverPreseed.ts), `preseedServer:281`, `upload:660`; [remoteSsh.ts](../src/ssh/remoteSsh.ts), строки 90–135.

`exec` не имеет deadline/cancellation; preseed проверяет signal только между некоторыми шагами. При зависшем exec «Отмена» не прервёт ожидание. Upload проверяет отмену только при поступлении progress, то есть зависшая передача может её не заметить. После отмены preseed всё равно открывается Remote-SSH окно; это намеренный fallback в коде, но текст прогресса не объясняет такую семантику.

**Предложение:** прерывать соответствующий channel/transfer по signal, ограничить время exec. Разделить «пропустить подготовку и подключиться» и «отменить подключение», не добавляя второй неожиданный результат одной кнопки.

**Приёмка:** зависание probe/upload/install + cancel → быстрое освобождение ресурсов; обычный fallback явно сообщён; отменённое подключение не открывает новое окно.

### A15 · P1 · Ошибка чтения SSH config может привести к перезаписи — код

**Где:** [remoteSsh.ts](../src/ssh/remoteSsh.ts), `ensureHostEntry:142`.

Любая ошибка `readFile(~/.ssh/config)` трактуется как отсутствие файла, после чего записывается новый config. Ошибка доступа/ввода-вывода не равна ENOENT. Конкурентные read-modify-write двух открытий также могут потерять добавленный блок.

**Предложение:** считать отсутствием только ENOENT, прочие ошибки показывать и прекращать запись; сериализовать изменения, сохранять файл атомарно и проверять, что исходная версия не изменилась.

**Приёмка:** EACCES/EIO → ноль записей; два параллельных открытия сохраняют оба блока и пользовательские записи; сбой записи оставляет прежний config.

### A16 · P1 · Редактирование описания может вернуть устаревшие настройки — код

**Где:** [index.ts](../src/commands/index.ts), `editNotebookDescription:506`; [apiClient.ts](../src/console/apiClient.ts), `modifyNotebook:177`.

**Приёмка:** каждое состояние из матрицы ниже имеет свой текст/действие; первая загрузка не утверждает, что данных нет; повторный refresh сохраняет строки и selection.

### A19 · P2 · Встроенный ноутбук не имеет состояний загрузки и восстановления — UX / код

### A20 · P2 · Подтверждение паузы и полезность переходов — UX

**Где:** [index.ts](../src/commands/index.ts), `pauseNotebook:182`; [notebookActions.ts](../src/views/notebookActions.ts), подсказка остановки; [notebookStatus.ts](../src/util/notebookStatus.ts), `RUNNING:19`.

### A21 · P2 · Не все ошибки имеют достоверное объяснение — код / UX

### A22 · P2 · Настройка ключа может завершиться частично — код / UX

**Где:** [sshConfig.ts](../src/ssh/sshConfig.ts), `configure:137`, `loadPrivateKey:152`, `uploadOwnPublicKey:202`, `offerSaveCopy:281`.

Configure очищает targets/endpoints даже при отменённом выборе файла. **Предложение:** получать и проверять нужные локальные данные до remote mutation; отмена до commit ничего не меняет. При частичном успехе сообщать, что уже изменено и как продолжить. Сужать права сохранённой копии после записи, silent-path возвращает ошибку вызывающему UI. Для зашифрованного ключа — поддерживаемый ввод passphrase либо точное сообщение об ограничении.

**Приёмка:** cancel на каждом шаге, несовпадающая пара, encrypted key, несуществующий путь, запись поверх 0644; отсутствие каскада одинаковых toast при восстановлении файлов.

### A23 · P2 · Explorer не получает часть изменений, ошибки SFTP маскируются — код

**Зачем:** A05–A06, A13. Исправление нескольких `.dispose()` по местам не предотвратит регистрацию позднего ресурса и утечки при двух открытиях.

**Целевая структура:** каждый существующий controller остаётся владельцем своих ready и in-flight ресурсов. Ключ включает context+uid; создание ресурса имеет явный owner и cleanup до публикации в map. `invalidate(uid)` и reset контекста симметричны для готовых и выполняющихся операций; `dispose()` окончателен. ### R05 · Переработка изменяющих файловых операций SFTP

**Зачем:** A01–A02, A23. Это кандидат на локальное переписывание `copy/rename/exists/writeFile`, потому что текущие алгоритмы небезопасны, а не только плохо организованы.

Copy/rename явно проверяют authority, совпадение и вложенность путей; учитывать root и сегменты пути, а не простой `startsWith`. Если симлинки позволяют обойти проверку вложенности, решить это через проверенный realpath-контракт либо явный отказ для неподдерживаемого случая.

**Порядок:** сначала минимальные исправления A01/A02 с тестами → прочитать API установленного ssh2 для replace/flags → удалить delete-before-rename → нормализовать ошибки → добавить события mkdir → только затем рассматривать bounded-memory copy. При отсутствии безопасного replace возвращать явную ошибку, не создавать «транзакцию» через удаление/восстановление, которая сама может потерять данные. Atomic write/copy — отдельное изменение поведения, его необходимость подтвердить сценариями, а не добавлять автоматически.

**Инварианты:** не писать на другой сервер, не удалять назначение до успешной безопасной замены, не копировать бесконечно в подкаталог, не сообщать FileNotFound при EACCES. Не объявлять многофайловый copy атомарным: при частичной ошибке сообщать, что уже было скопировано, и не удалять ранее существовавшие файлы.

**Проверка:** новый `test/unit/sftpFs.test.ts`, существующий `sftpErrors.test.ts`; `pnpm exec vitest run test/unit/sftpFs.test.ts test/unit/sftpErrors.test.ts` и `pnpm typecheck`. Инъекции failure на каждой mutation, файл→себя, каталог→потомка, разные authority, существующий target, permission denied. Поддержку replace подтвердить на тестовом шлюзе до объявления готовности. **Замещает:** этап 1 и файловую часть A23; начать первым минимальным исправлением, завершать отдельно от R04.

### R06 · HTTP-транспорт с конечным временем жизни и точными ошибками

**Зачем:** A09–A10, часть A21. Transport — небольшое место, где локальная переработка надёжнее добавления ещё нескольких разрозненных catch.

**Граница:** `src/console/consoleHttp.ts`, `src/console/apiClient.ts`, `src/console/pollLoop.ts`, передача cancel из команд. Сохранить injected `HttpFetch`, текущий HTTPS agent и механизм обхода patch `http.request`, уже проверенный `consoleHttp.test.ts`. Не заменять транспорт на fetch/axios: это потеряет существующие свойства корпоративного окружения.

**Целевая структура:** request имеет общий deadline, AbortSignal и одну процедуру завершения, которая снимает таймеры/listeners. Completion учитывает request errors, response errors/aborts и полный end. API client отделяет transport, HTTP status, ошибку JSON/shape и действительно пустой успешный ответ. Endpoint-specific guards проверяют только необходимые поля; универсальная schema-библиотека не нужна.

**Порядок:** локальный сервер с partial response → deadline/abort и cleanup → классификация schema failures → прокинуть signal через API в poll → согласовать окончательный 401 с R03. Сохранить исходную причину ошибки. Для shared in-flight списка определить контракт отмены: отмена одного poll не должна убить запрос дерева/kernel; отделить ожидание подписчика от жизни общего запроса либо сделать отменяемый запрос операции отдельным. Не присоединять общий request к signal первого случайного потребителя.

**Инварианты:** promise завершается ровно один раз; timeout ограничивает всю операцию; один cancelled consumer не ломает остальных; malformed response не превращается в «нет воркспейсов»; мутации не повторяются транспортом автоматически.

**Проверка:** `pnpm exec vitest run test/unit/consoleHttp.test.ts test/unit/apiClient.test.ts test/unit/pollLoop.test.ts` и `pnpm typecheck`. Truncated body, slow chunks, abort до/после headers, два подписчика и отмена одного, malformed JSON, gzip error, 401/403/429. **Замещает:** transport-часть этапа 3; контракт отмены нужен R02, итоговый auth route согласуется с R03.

### R07 · Разделение подготовки Remote-SSH по границам побочных эффектов

**Зачем:** A14–A15. Это второй эшелон: `serverPreseed.ts` уже имеет чистые helpers, инъекции и 28 тестов. Его размер сам по себе не повод переписывать download/cache/install алгоритмы.

**Граница:** `src/ssh/serverPreseed.ts`, `src/ssh/remoteSsh.ts`, `src/ssh/connection.ts`, `src/ssh/sshConfigFile.ts`. Если после добавления отмены файл остаётся трудно проверяемым, допустим новый `src/ssh/serverDownload.ts` только для существующих download/cache функций; такого отдельного модуля сейчас нет. Не менять URL templates, shell install layout, cache format и deferral policy в структурном переносе.

**Целевая структура:** pure product/path/script helpers остаются отдельно от выполнения; orchestration вызывает probe/download/upload/install с одним cancellation/deadline-контрактом; SSH config read-modify-write — отдельная функция с точной обработкой ENOENT и защитой от потери обновлений. Background download явно принадлежит extension lifetime, а foreground observer можно отменить без случайного прерывания другого потребителя общей загрузки.

**Порядок:** тест зависшей стадии и отмены → cancellation exec/upload → явная семантика skip/cancel → безопасное изменение SSH config → при необходимости механический перенос download функций с сохранением экспортируемых контрактов. Не объединять смену алгоритма загрузки и перенос в один diff.

**Инварианты:** cancel не ждёт следующего progress callback; cancelled operation не открывает окно; deferred task не вызывает unhandled rejection; второй consumer не теряет общую загрузку при отмене первого; ошибка чтения config не приводит к записи нового файла.

**Проверка:** `pnpm exec vitest run test/unit/serverPreseed.test.ts test/unit/remoteSsh.test.ts test/unit/connection.test.ts` и `pnpm typecheck`. Fake exec/transfer зависают до abort; сценарии concurrent download, deferred→foreground, EACCES и двух config updates. **Замещает:** этап 7 и config-часть этапа 6; выполнять после согласования lifetime в R04.

## Открытые решения и ограничения

- Для host-key trust нужен подтверждённый источник fingerprint/политика первого подключения.
- Для безопасного replace и optimistic concurrency нужны фактические возможности SSH gateway и backend; не подменять их предположениями.
- Для logout рекомендовано закрывать управляемый SFTP; политика независимого Remote-SSH окна должна быть явно описана.
- Минимальная версия редактора, deep links консоли и доступность логов в busy-состояниях ещё требуют проверки. Это не готовые подтверждённые контракты.
- Unit-прогоны не покрывают реальное встраивание iframe, cookie policy, SSO нескольких окон, UI accessibility и минимальный Extension Host. Матрицу выше нужно выполнить до объявления этих сценариев исправленными.
- Приоритет выполнения: сначала A01–A02, затем изоляция контекста/соединений, auth/transport и lifecycle, после — визуальные и текстовые улучшения. Задачи R01–R07 описывают рекомендуемый вариант частичного рефакторинга вместо накопления локальных исправлений; полное переписывание приложения и новые зависимости не предлагаются.
